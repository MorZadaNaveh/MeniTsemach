# Authentication Security Setup

This project now uses server-side authentication with:

- Password hash verification (`bcrypt`)
- TOTP second factor (`otplib`, authenticator app)
- Signed access tokens (`JWT`)
- Protected backend functions (`store`, `analyze`, `extract-appendices`)
- Office-level data isolation in storage (`officeId` key prefix)

## Required Environment Variables

Set these in your Netlify environment (and locally for `netlify dev`):

- `JWT_SECRET` (required, 32+ chars)
- `ADMIN_EMAIL` (required for first bootstrap user)
- `ADMIN_PASSWORD` (required for first bootstrap user)
- `ADMIN_TOTP_SECRET` (optional; autogenerated if missing)
- `ADMIN_OFFICE_ID` (optional, default: `default-office`)
- `ADMIN_ROLE` (optional, default: `admin`)
- `ALLOW_DEMO_LOGIN` (optional, temporary only)
- `DEMO_EMAIL`, `DEMO_PASSWORD`, `DEMO_OTP` (optional demo credentials)

## First Login Flow

1. Enter email + password in login screen.
2. Backend validates password hash.
3. Backend returns short-lived OTP challenge.
4. Enter 6-digit code from your authenticator app.
5. Backend verifies TOTP and returns access token.
6. Frontend stores access token in `sessionStorage` and sends it on API calls.

## Security Notes

- Do not commit real secrets to git.
- Use long random values for `JWT_SECRET`.
- Rotate admin bootstrap password immediately in production.
- Demo login can be kept temporarily by setting `ALLOW_DEMO_LOGIN=true`.
- For production go-live, set `ALLOW_DEMO_LOGIN=false`.

## Future Implementation (Refresh Token)

Add this in the next auth hardening phase:

- Refresh-token rotation with one-time-use tokens
  - Issue short-lived access token (e.g. 15m) + long-lived refresh token (e.g. 7d)
  - Store only a hashed refresh token server-side
  - On refresh: invalidate old token and issue a new refresh token + access token
  - If an old refresh token is reused, revoke all active sessions for that user
- Dedicated endpoints:
  - `POST /.netlify/functions/auth` action `refresh`
  - `POST /.netlify/functions/auth` action `logout`
- Session persistence model:
  - `sessionId`, `userId`, `officeId`, `refreshTokenHash`, `expiresAt`, `revokedAt`, `ip`, `userAgent`
- Client behavior:
  - Keep access token in memory/session
  - Keep refresh token in `HttpOnly`, `Secure`, `SameSite=Strict` cookie
  - Auto-refresh access token on `401` (single retry), then force re-login if refresh fails
